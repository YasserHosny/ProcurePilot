# ProcurePilot — R2.2 Mobile MVP UI Mockup Prompts for Google Stitch

> Text prompts for generating high-fidelity mockups for **Release R2.2 (Mobile MVP)** only —
> scoped to `specs/009-mobile-app-mvp/spec.md`, not the full Phase 2 mobile screen set.
> Base style: Material Design 3, clean enterprise SaaS, light theme by default, WCAG 2.1 AA,
> bilingual (English + Arabic RTL ready).
>
> This supersedes the "Mobile Prompts — Phase 2" section of `ui-mockup-prompts.md` for this
> release. Of that set's 12 screens, four are dropped outright as R2.3 scope (Scan/Photo Capture,
> Approval Queue, Approval Detail, Delivery Confirmation — spec §"Out of scope", roadmap §12.6),
> and Alerts is dropped because no R2.2 user story needs an alerts inbox. Five are **corrected**,
> not merely reused, because the master versions depicted things this release doesn't ship or
> omitted a state this release needs: Home — Approver (dropped its "Review now" action button —
> FR-009), New Request (dropped camera/barcode controls — spec's R2.3 exclusion), Home — Branch
> Manager (dropped the Alerts tab and the redundant floating action button now that "New request"
> is already the hero card), My Requests (narrowed the status set to R2.1's actual five, added an
> offline "Queued" state, split into a dedicated list screen and a dedicated detail screen), and
> Settings (narrowed notifications to decision-only, dropped delivery/alerts preferences). Only
> Login/Biometric Unlock needed a genuine split rather than a correction — see R2.2-M1/M1b below.

---

## Review status

Reviewed by both `agy` (UI/UX and visual-design fit for Stitch) and `codex` (scope/spec fidelity
against `specs/009-mobile-app-mvp/spec.md` and the roadmap) before this version. Both reviews were
read-only critiques; this version is the result of applying their findings. Summary of what
changed from the first draft:

- Split every prompt that described more than one temporal/visual state into separate,
  single-frame prompts (Login now two prompts; My Requests list and detail are now two prompts;
  Low-Stock Report's confirmation and offline-queued states are now named variants of one frame,
  not composited into it).
- Removed the low-stock screen's product-level stock indicator dot — it implied an inventory
  tracking system this release doesn't have (FR-006 is a one-tap signal, not a stock ledger), and
  it was also color-only, which fails WCAG 1.4.1.
- Added the offline/queued state to Low-Stock Report (FR-011/FR-012 apply to both requests and
  low-stock reports, not requests alone) and a declined-notification-permission state to Settings
  (FR-008 / Story 4 scenario 3).
- Reframed every "must not show X" instruction as a positive description of what the screen does
  show, since negative prompts are unreliable with generative image models.
- Fixed factual/consistency errors: Arabic needs its own typeface (Roboto has no Arabic glyph
  coverage), Material's actual minimum touch target is 48×48 dp not 44×44, chip/badge text can go
  to 12sp under MD3's own type scale, status colors reference the actual indigo token rather than
  an unrelated "blue," and the warning color now has an explicit hex value.

## How to use these prompts in Stitch

Generate **R2.2-DS (Design System) first**, in its own project. Then generate the nine screen
prompts below, in order, in that same project, so each one draws on the design system's palette,
type scale, and component styles instead of improvising its own — this is what keeps nine
independently-generated screens looking like one app. If a screen comes out visually inconsistent
with the design system, regenerate it referencing the design system output directly rather than
adjusting the prompt text alone.

## R2.2-DS — Design System (generate this first)

Generate a mobile design system reference sheet for a Flutter app called **ProcurePilot** — a B2B
procurement SaaS. Tone: clean, trustworthy, efficient enterprise software; not playful, not
consumer-flashy. Material Design 3, light theme, WCAG 2.1 AA, built to support English and Arabic
(full RTL) from the same components. This is a single reference sheet — palette swatches, type
samples, and component variants laid out together — not an app screen.

**Color roles** (show each as a labeled swatch): Primary — indigo `#4F46E5` (filled buttons,
active navigation, links). Accent/Warning — amber `#F59E0B` (highlights and warning states share
this token). Success — green `#10B981`. Error — red `#EF4444`. Neutral surface — white screen
background with a very light warm-grey for outlined cards and dividers. On-color text — white on
filled indigo/error buttons, dark neutral-grey body text on light surfaces.

**Typography** (show a sample of each, in both languages side by side): Latin text in Roboto,
Arabic text in Noto Sans Arabic (or Cairo) — never Roboto for Arabic, it has no Arabic glyphs.
Material 3 type scale: a headline size for screen titles, a title size for card/section headers, a
body size (14sp minimum) for default text, and a label size (may go to 12sp) for chips, badges,
and button text.

**Spacing and shape**: 8dp base grid, 16dp standard screen padding, 48×48dp minimum touch target
on every interactive element, 12dp corner radius on cards and buttons (rounded but not playful).

**Elevation**: prefer flat or outlined cards over heavy shadows — this is enterprise software, not
a consumer app. One consistent elevation level reserved for anything that genuinely lifts off the
page (dialogs, bottom sheets) — nothing else uses a shadow.

**Iconography**: Material Symbols, outlined style by default; filled only for an active/selected
state (e.g. the current bottom-navigation tab).

**Core components to show, each in one variant that every later screen will reuse**:
- Buttons: filled primary (indigo), outlined secondary, text/ghost tertiary — same height and
  corner radius across all three.
- Status chip: a pill combining an icon + label + color together — never color alone. Show all six
  variants this app needs: Draft (grey, pencil icon), Submitted (indigo, clock icon), Approved
  (green, check icon), Rejected (red, X icon), Withdrawn (grey, undo icon), Queued (amber, small
  clock/sync icon).
- Cards: two variants side by side — a filled "hero" card style (for a screen's single primary
  action) and an outlined card style (for everything secondary).
- List tile: leading icon, title, subtitle, optional trailing chip or switch.
- Bottom navigation bar: three items (Home, Requests, Settings) — outlined icon when inactive,
  filled icon with an indigo tint when active.
- Top app bar: leading back/close icon, title text — show both a left-to-right (English) and a
  mirrored right-to-left (Arabic) version side by side, since every directional element (back
  arrows, chevrons) must flip correctly.
- Form field: an outlined Material text field showing its label, hint, and error states.

## R2.2-M1 — Login (First Sign-In)

Generate a mobile login screen for a Flutter app, for a member who has not yet signed in on this
device. Top: app logo and tagline. Center: email and password fields and a filled primary
"Sign in" button — this is the sole focal point of the screen, no competing biometric icon or
prompt anywhere on it. Bottom: language toggle (EN / AR). Use Material Design 3, light theme,
rounded corners, and large touch targets. No sign-up or social-login affordance (accounts are
created on web).

## R2.2-M1b — Enable Biometric Unlock (post-sign-in) and Returning-Device Unlock

Generate two related states in one Material Design 3 bottom-sheet pattern:

1. **Enable prompt**, shown once immediately after a successful first sign-in on a device that
   supports biometrics: a centered fingerprint/face icon, a headline "Unlock faster next time?",
   body text explaining biometric re-entry replaces typing a password, and two buttons — a filled
   primary "Enable" and a text "Not now."
2. **Returning-device unlock**, shown on every later app open for a member who enabled it: a
   full-screen state with the app logo at top, a centered biometric icon mid-screen with the label
   "Unlock with biometrics," and a single small text link below it, "Use password instead" — the
   password fields themselves are not shown unless that link is tapped.

Depict these as two clearly labeled panels side by side in the same generation, not blended into
one screen.

## R2.2-M2 — Home (Branch Manager)

Generate a role-aware mobile home screen for a branch manager. Top greeting, "Good morning,
Khaled." Primary action: one large filled hero card, "New request," spanning the full width,
visually dominant over everything else on the screen. Below it, a 2-column grid of two smaller
outlined cards: "Low stock report" and "My requests" — clearly secondary to the hero card, not
competing with it for attention. Below that, a "Recent activity" section: a vertical list of
Material list tiles, each with a leading icon, a primary line naming the request (e.g. "Packaging
& tape — 2 items"), a timestamp ("10m ago"), and a trailing status chip; include at least one tile
whose trailing chip reads "Queued" in a small amber pill instead of a normal status, to depict the
offline-sync state alongside ordinary ones. Bottom navigation bar: Home, Requests, Settings — no
Alerts or Approvals tab, neither exists for this role in this release.

## R2.2-M4 — New Request

Generate a mobile screen for creating a purchase request, structured as two visually distinct
sections. **Header section** (top, shown once): a branch indicator — read-only text if the member
has exactly one branch, otherwise a dropdown selector — and a required-by date picker, side by
side or stacked, clearly separate from the items below. **Line items section** (below, repeatable):

recent-item tap), a quantity stepper, and an optional per-line note field with a small trailing

normal idle state: an outlined "Save draft" and a filled primary "Submit request" (do not depict a
loading/spinner state — that is a transient micro-interaction, not this screen's primary frame).

Generate a mobile screen reached by tapping "Low stock report" from a single product's own detail

outcomes are visually distinguishable from each other and from a normal success state.

## R2.2-M6 — My Requests (List)

Generate a mobile screen showing a vertical list of the signed-in member's own requests, newest
first. Each card has a primary header line identifying the request (e.g. "Request · Cleaning
Supplies" or the first line item's name if a request has only one), a secondary line with the
line-item count and required-by date (e.g. "3 items · Due 18 Sep"), and a trailing status chip

shows an additional small amber "Queued" chip in place of its status chip, matching R2.2-M2's
treatment. Tapping a card opens R2.2-M6b.

Also generate an **empty-state variant** of this same screen: a simple illustration, the headline
"No requests yet," and a filled primary "New request" button — shown when the list has no items.

## R2.2-M6b — Request Detail & Decision

Generate the detail screen reached by tapping a card on R2.2-M6, or by tapping a push notification

## Global style notes

*(R2.2-DS above is what actually generates the design system in Stitch; this list is the
quick-reference the screen prompts above were written against — keep it in sync if R2.2-DS
changes.)*

- Light theme by default; dark mode not in scope for R2.2.
- Primary color: indigo `#4F46E5`; accent: amber `#F59E0B`; success: green `#10B981`;
  warning: amber `#F59E0B` (same token as accent); error: red `#EF4444`. Status chips MUST use
  these exact tokens, not an unrelated color like plain "blue."
- Fonts: Roboto for Latin (English) text; Noto Sans Arabic (or Cairo) for Arabic text — Roboto has
  no Arabic glyph coverage, so Arabic screens must specify their own typeface.
- Maintain WCAG 2.1 AA contrast. Body text minimum 14sp; badge, chip, and caption labels may go
  as small as 12sp per Material's own type scale, but never smaller. Never convey status by color
  alone — always pair a color with an icon or a text label.
- Minimum touch target 48×48 dp (Material Design 3's actual minimum interactive dimension, not iOS's 44).
- Layouts must be RTL-ready; avoid left/right directional labels, use start/end; mirror any
  directional icon (back arrows, chevrons) in the Arabic variant.
- Use real-ish placeholder data relevant to small-business procurement (cleaning supplies,
  packaging, office products).
