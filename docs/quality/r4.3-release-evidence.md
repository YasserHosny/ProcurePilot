# R4.3 Release Evidence

Date: 2026-09-25, updated 2026-09-26
Release: Automated RFQ Sourcing and Guarded Autonomous Workflows
Gate posture: G3 remains unmet

## Release Decision

R4.3 is the fourth and final release of Phase 4 (Predictive Procurement), sitting directly on
Constitution Principle III (Human Authority Over Automation, NON-NEGOTIABLE). It introduces two
already-permitted automation verbs — **route** (dispatching an RFQ is a request for information,
not a commitment) and **prepare** (auto-creating a draft is exactly what R4.0's reorder-proposal
"prepare request" action already does, human-initiated) — and lets the system, under tight,
explicit, owner-configured guardrails that are off by default, initiate that same prepare step
itself. In no configuration, manual or automatic, does R4.3 create, submit, or transmit a
purchase order; every path produces an ordinary `purchase_request` entering the existing,
unmodified human approval workflow. This is executable, not just asserted in the plan's prose —
see `test_rfq_guardrail_boundary.py`.

## Delivered Contract

`POST /rfq` creates an RFQ (one or more lines, one or more recipient suppliers); `POST /rfq/{id}/
send` dispatches it by email via Mailgun (ADR-018, reusing the existing inbound vendor
relationship rather than adding a second one); `GET /rfq/{id}/responses` lists captured responses
for comparison; `POST /rfq/{id}/prepare-request` turns a chosen response into a draft purchase
request; `GET /rfq` lists RFQ history; `POST`/`GET`/`PATCH /rfq/guardrails` manage owner-only
auto-preparation guardrails. Full field detail is in `docs/architecture/api-specification.md` and
`docs/architecture/data-dictionary.md` (R4.3 sections).

- Any owner or buyer may create and send an RFQ; a recipient supplier with no on-file contact
  email is excluded and reported back, never silently dropped or failing the whole call.
- Reads (responses, history) are scoped to the RFQ's creator, or owner/buyer for tenant-wide
  oversight (FR-016) — enforced by RLS, mirroring `analyst_conversation`'s established pattern,
  not application-layer filtering.
- `POST /rfq` and `POST /rfq/{id}/prepare-request` both require an `Idempotency-Key`; a replay
  returns the identical resource rather than creating a second one — `create()`'s idempotency was
  found during review to only guard against concurrent duplicate calls, not a genuine retry after
  the original transaction already committed, and was fixed to a true lookup-before-insert check.
- `auto_preparation_event` is append-only: no role, including `service_role`, has `UPDATE`,
  `DELETE`, or `TRUNCATE` on it.
- Guardrail management is owner-only, enforced by both RLS and an explicit application-layer
  check; a guardrail configuration with a zero, negative, or otherwise-degenerate maximum order
  value is refused at creation (FR-013).

## Business Validation

**US1 (send)** — an RFQ is created and dispatched to every recipient with an on-file email,
tracked per-recipient (`rfq_recipient.status`), with a stable, deterministic outbound `Message-ID`
per recipient used later for reply threading.

**US2 (capture)** — an inbound reply is matched to an open RFQ recipient by thread headers
(`In-Reply-To`/`References` against `rfq_recipient.outbound_message_id`) inside the existing async
ingestion worker, additively alongside the existing supplier/quotation matching — a matched reply
still produces an ordinary quotation through the unmodified extraction pipeline, plus a linked
`rfq_response` row. A reply matching no open RFQ falls through unchanged (FR-006); an
arithmetic-mismatch response gets no RFQ-specific exemption from the existing mandatory review
task (FR-005).

**US3 (compare, manually prepare)** — `list_responses()` joins each response's quotation lines
through the existing extraction/matching pipeline's `match_decision` rows, surfacing an explicit
`pending_match` flag for a line whose product match hasn't completed yet rather than omitting it.
`prepare_request()` calls the same `RequestsService.create_request()` a human's manual purchase
request uses, then overrides the new line(s)' `estimated_unit_price` with the response's actual
quoted price — not a landed-cost estimate, a deliberate difference from the reorder-proposal path
— and sets `purchase_request.source_rfq_response_id` so the draft cites which response it came
from (FR-008). The RFQ's own status moves to `converted`, a real gap found during review (T027
originally never made this transition).

**US4 (guardrails)** — an owner configures zero or more guardrails (max order value, supplier/
category allow-lists, minimum response count, max price variance), off by default per tenant.
When a captured response satisfies every condition of an enabled guardrail — the RFQ still open,
enough total responses received, every line matched, currency matching exactly (FR-018, never a
cross-currency comparison), supplier (and, if configured, category — confirmed with the product
owner to fail closed, since no product-category data exists anywhere in this schema) allowed,
total within the configured maximum, and price within the configured variance of the tenant's own
recent purchase history for that product (no history at all is treated as ineligible, never
guessed) — and it is the single lowest-priced such response (a tie never fires, FR-012), the
system calls the exact same `prepare_request()` path, acting as the guardrail's own creator via
the service-role credential this app already holds for system-initiated writes, and records an
append-only `auto_preparation_event` plus a dedicated `rfq.auto_prepared` audit event. Disabling
or tightening a guardrail afterward never retroactively touches an already-fired event (FR-014).

**US5 (history)** — every RFQ visible to the caller, cursor-paginated, with recipient/response
counts and — once converted — the purchase request it produced.

## Data and Isolation

Migrations across Phases 1–6 add `rfq`, `rfq_line`, `rfq_recipient`, `rfq_response`,
`auto_preparation_guardrail`, `auto_preparation_event`, plus `supplier.contact_email` and
`purchase_request.source_rfq_response_id`. All six new tables have forced RLS, composite
tenant-pinned foreign keys, and the creator-plus-owner/buyer read pattern established by
`analyst_conversation`. `auto_preparation_event` has no update/delete/truncate grant for any
role. A late, real gap found during Phase 6 review: `purchase_request_line`'s original
`estimated_unit_price_source_landed_cost_id` pairing constraint forced every priced line to cite
a landed-cost row, which only held while landed cost was the sole estimation source — relaxed via
migration rather than synthesizing a fake landed-cost row to satisfy it.

Dedicated isolation suite (`test_rfq_isolation.py`): cross-tenant invisibility for all six tables,
append-only enforcement on `auto_preparation_event` (`UPDATE`/`DELETE` both raise
`InsufficientPrivilege`), cross-tenant `INSERT` rejection — passing against real Postgres.

A second, independent RLS finding from review: the async ingestion worker's own tenant-scoped
session (`_act_as_tenant`, used throughout `orchestrator.py`) carries only `tenant_id`/`role`
claims, not `member_role` or `sub` — sufficient for `quotation`/`ingestion_email_log`'s plain
tenant-only RLS policies, but not for `rfq_recipient`/`rfq_response`/`auto_preparation_guardrail`,
whose policies require a real membership/owner-buyer claim. The response-capture and guardrail-
evaluation paths inside the worker use `set local role service_role` with explicit `tenant_id`
filters on every statement instead, resetting back to `authenticated` afterward — the same
pattern already established elsewhere in this codebase (`accounting_sync_worker.py`,
`pos_sync_worker.py`) for system-initiated writes, not a new one invented for this release.

### Post-merge findings (T047 live walkthrough preparation)

R4.3 (PR #26) and its documentation follow-up (PR #27) merged and passed all CI gates, but
preparing the live hosted walkthrough surfaced four further defects, none caught by the review
above because each required tracing the real, end-to-end path a human or a real external system
(Mailgun, the hosted database's actual applied schema, a browser driving the real UI) would take —
exactly the gap a live walkthrough exists to close. All four are fixed and merged.

- **RFQ dispatch emails had no working reply path (PR #28).** `RfqService.send()` called
  `mailer.send()` with no `Reply-To` header; `MailgunMailer` sends `From:
  noreply@{MAILGUN_SENDING_DOMAIN}` — a different domain than any tenant's actual inbound capture
  address (`tenant_email_config.forwarding_address`). A real supplier hitting "Reply" would have
  sent to an address no tenant owns, which the inbound webhook silently accepts and drops (by
  design, to avoid leaking valid addresses — see `router.py`'s `_lookup_tenant_by_address`). Every
  existing capture test bypassed this by calling `process_inbound_email()` directly with
  `tenant_id` already known, never exercising the real recipient-based tenant lookup. Fixed by
  looking up the tenant's `forwarding_address` and setting it as `Reply-To` (with a plain-text
  fallback in the email body); the new test posts to the real `/webhooks/inbound-email` router
  endpoint to prove tenant resolution actually works, closing that blind spot.
- **R4.3's own migrations were never applied to the hosted database.** Deploying the container
  images (Deploy Backend/Deploy Frontend) only updates the running application code — it does not
  run `pnpm db:migrate`. Confirmed directly (`information_schema.columns`/`.tables`): none of
  `rfq`, `rfq_line`, `rfq_recipient`, `rfq_response`, `auto_preparation_guardrail`,
  `auto_preparation_event`, or `supplier.contact_email` existed on hosted despite the app
  containers already running R4.3's code — any RFQ endpoint would have failed outright. Applied
  the 6 pending migrations via `pnpm db:migrate` against the hosted `DATABASE_URL`; verified
  schema afterward and confirmed `/rfq/history` renders with no errors.
- **Create RFQ's supplier picker could not select a real supplier (PR #29).** The multi-select's
  options were hardcoded, literal placeholder values (`create.component.html`: `<option
  value="sup-1">Supplier 1</option>`/`sup-2` — never populated from real data). There was no way
  to create an RFQ against a real supplier through this screen at all; every submission sent those
  literal strings as `recipient_supplier_ids`. Rewritten to use real Material components with
  supplier/product pickers backed by `ApiService.suppliers()`/`.products()` — the same service
  every other screen already uses — plus full `en`/`ar` i18n coverage (previously absent
  entirely) and a navigation entry point on RFQ History (previously unreachable except by typing
  the URL). One further gap found and fixed during independent review of the dispatched diff: the
  new nav button referenced an i18n key (`rfq.history.createRfq`) that was never added to either
  translation file.
- **`supplier.contact_email` had no backend API support at all, despite the frontend now sending
  it (also PR #29).** The catalogue module's `Supplier`/`SupplierCreate`/`SupplierUpdate` Pydantic
  models never gained the field — `SupplierCreate`/`SupplierUpdate` inherit from `StrictApiModel`
  (`extra="forbid"`), so once the Create RFQ fix's companion change to the Supplier form started
  sending `contact_email` on every create/update call, the backend rejected every request with a
  422. This was not a hidden edge case: it broke supplier creation and editing entirely, for every
  user, regardless of whether the new field was filled in. Caught by a real (non-flaky —
  reproduced identically twice, including on CI's own internal retry both times) E2E failure on
  `phase-one-value-path.spec.ts`, not by any unit or contract test, since none of those exercise
  the full Angular-form-to-FastAPI-schema round trip. Fixed by adding `contact_email` to all three
  models and to `SUPPLIER_COLUMNS`/the `_supplier()` row mapper/both
  `create_supplier()`/`update_supplier()` — mirroring `payment_terms`'s existing wiring exactly,
  the same gap `RfqService` had already independently worked around via raw SQL rather than these
  shared models.
- **Real Mailgun inbound webhook payloads were rejected outright, 422, every time (PR #32) — the
  most significant finding of the whole walkthrough.** `router.py`'s `inbound_email_webhook()`
  read `form.get("body-mime")` to reconstruct the original message, but Mailgun's actual webhook
  payload (confirmed via Mailgun's own "Send a sample POST" diagnostic tool against a controlled
  endpoint, not assumed from documentation) has no `body-mime` field at all — only `body-plain`,
  `body-html`, `message-headers` (a JSON array of `[name, value]` pairs), `attachment-count`/
  `attachment-N`, and the signature fields. Every existing test set `INGESTION_EMAIL_PROVIDER=stub`,
  so this was invisible to the whole suite; it would have silently broken **all** real inbound
  email for both R3.0's quotation inbox and R4.3's RFQ capture, the day either first tried to run
  against real Mailgun traffic. Fixed by reconstructing a valid RFC822 message from
  `message-headers`/`body-plain`/`body-html`/`attachment-N` instead. A second bug surfaced by the
  fix itself, not by any pre-existing test: copying `Content-Type`/`Mime-Version` verbatim from
  `message-headers` before calling `EmailMessage.set_content()` raises `TypeError: set_content not
  valid on multipart` whenever the source message is multipart — which is the **normal**, not
  edge, case for any ordinary Gmail reply (multipart/alternative: text/plain + text/html by
  default). Reproduced standalone before fixing; fixed by skipping `content-type`/`mime-version`/
  `content-transfer-encoding` when copying headers and letting `set_content()`/`add_alternative()`
  manage them. The new test (`test_mailgun_webhook.py`) posts a byte-for-byte realistic
  `multipart/form-data` payload, including a real PDF attachment and a genuine multipart
  `Content-Type` header, through the real `/webhooks/inbound-email` route.

## Live Hosted Walkthrough

Updated 2026-09-26. The send→capture round trip that was blocked as of 2026-09-25 (no verified
Mailgun sending domain) is now proven end to end against the real hosted app
(`procurepilot.iron-sys.com`, `ProcurePilot Test` workspace) with a real external mail provider —
not a stub, not a direct-call bypass of the ingestion path. Getting there surfaced five further
real defects/gaps beyond the four in "Post-merge findings" above, all found by tracing the actual
path a real supplier email takes rather than by inspection. R4.3's walkthrough has now found more
genuine, previously-undetected production defects than any prior release's — the walkthrough is
this release's most productive verification step, not a formality performed after the fact.

### Mailgun set up as a real outbound/inbound provider

`mail.procurepilot.iron-sys.com` was added and verified as a Mailgun sending/receiving domain
(chosen over `procurepilot.iron-sys.com` due to an existing CNAME conflict with the live web app,
and over a shorter alternative to keep this product's mail distinguishable from other products on
the same `iron-sys.com` domain). SPF/DKIM/tracking CNAME were provisioned via GoDaddy Domain
Connect; MX records (`mxa.mailgun.org`/`mxb.mailgun.org`, priority 10) were added manually, since
Domain Connect only covers sending records. Inbound Route: catch-all → forward to
`https://procurepilot-api.iron-sys.com/api/v1/webhooks/inbound-email`. The hosted backend
container was configured with `RFQ_MAILER_MODE=mailgun`, `MAILGUN_SENDING_DOMAIN`,
`MAILGUN_API_KEY`, `INGESTION_EMAIL_PROVIDER=mailgun`, `MAILGUN_SIGNING_KEY`, and
`INGESTION_EMAIL_DOMAIN`, all set to real values (API key and signing key from Mailgun's Account
Settings → API Security page, not the per-domain Sending Keys tab, which is a separate, unused
feature). `POST /rfq/{id}/send` against the real hosted API now returns a real Mailgun
`outbound_message_id` instead of the `fake-...@stub.mail` shape seen on 2026-09-25 — outbound is
confirmed live.

### Further gaps found while proving the round trip

- **`tenant_email_config` had never been set up for the test tenant.** `RfqService.send()`'s
  Reply-To logic (PR #28) correctly found no enabled row and left `Reply-To` unset — working
  exactly as designed, not a code bug. Replies therefore went to `noreply@...`, matching no
  tenant, and were silently 202-and-dropped by `_lookup_tenant_by_address`'s deliberate
  no-existence-leak behaviour. This is a genuine missing per-tenant onboarding step, not a defect:
  every tenant onboarding a real inbound mailbox needs to call `PUT /tenants/email-config` then
  `POST /tenants/email-config/enable` once. Fixed for this tenant directly via the API, yielding
  `forwarding_address: procurepilot-test@mail.procurepilot.iron-sys.com`.
- **Mailgun's real webhook payload shape had two separate bugs, fixed in PR #32** (see "Post-merge
  findings" above for the full detail) — found only once a real Mailgun webhook, not a synthetic
  test payload, hit the endpoint.
- **`email_ingestion_worker.py` was never deployed anywhere — now fixed and confirmed running.**
  This standalone script (`apps/api/src/procurepilot_api/workers/email_ingestion_worker.py`,
  `tick()`/`run_loop()`/`main()`) polls `ingestion_jobs` for `job_type='email_ingest'` via
  `FOR UPDATE SKIP LOCKED`. It was never invoked by the FastAPI app, and no GitHub Actions workflow
  referenced it (`deploy-extraction-worker.yml` deploys a different, unrelated worker/job type).
  `select job_type, status, count(*) from ingestion_jobs group by 1, 2` on the hosted database
  showed **zero** `email_ingest` jobs had ever completed before this session — meaning the entire
  automated email-ingestion feature, for both R3.0 (quotation inbox) and R4.3 (RFQ capture), had
  likely never processed a real inbound email in this deployment before tonight. Initially worked
  around by running `tick()` manually against the hosted `DATABASE_URL`; genuinely fixed via
  PR #34, which adds `infra/docker/email-ingestion-worker.Dockerfile` (same package layout as
  `api.Dockerfile`, CMD runs `run_loop()` instead of `uvicorn`) and
  `.github/workflows/deploy-email-ingestion-worker.yml` (mirrors `deploy-extraction-worker.yml`,
  targeting the same `BUNNY_WORKERS_APP_ID` bunny.net Magic Containers app). A
  `procurepilot-email-ingestion-worker` container was created in that app and the deploy pipeline
  confirmed working end to end. **Confirmed running autonomously**: a fresh, real `ingestion_jobs`
  row (job `d8dc07d0-bc1a-4e40-859e-be847fc971c5`, reusing a genuine previously-stored raw email)
  was queued as `pending` and deliberately left untouched — it was claimed and completed by
  `locked_by='email_ingestion_worker'` within the container's own 15-second poll interval, with
  **no manual `tick()` invocation this time**. This is the first time this deployment has processed
  an inbound email without a human manually running the worker.
- **Full line-item extraction from a real attached document — now proven accurate, not just
  reachable.** The extraction-worker's Bedrock→Azure DI fallback chain (`worker.py`) initially
  surfaced only the generic `"AZURE_DI_ENDPOINT and AZURE_DI_KEY are required"` error, masking a
  Bedrock failure only visible in the hosted container's own logs. After the user corrected the
  hosted extraction-worker container's configuration mid-session, a retry (`POST
  /quotations/{id}/retry-extraction`) reached Azure DI itself and failed with a more specific
  `InvalidContent: The file is corrupted or format is unsupported` — confirming Azure DI was
  reachable, given *some* input, but not yet tested with a genuine document. Composing an email
  reply with a true MIME attachment turned out to be unreachable with the available tools (the
  Gmail MCP connector's `reply` has no attachment parameter; Google Drive's `create_file` only
  inserts a share *link* into the body, confirmed empirically to produce no attachment for the
  pipeline at all). Bypassed the email transport entirely instead: uploaded documents directly
  through the real hosted `POST /api/v1/capture` endpoint — the same extraction-worker and
  database path the RFQ capture flow uses, decoupled from Mailgun/Gmail. First attempt, a plain
  PDF with text positioned via raw `drawString` calls (no table borders, no invoice-template
  layout): `extraction_job.status='succeeded'`, `attempted_provider='azure_di'`, but **zero**
  extracted lines and null header fields — Azure's `prebuilt-invoice` model didn't recognise it as
  an invoice, and its table-extraction fallback found no table structure either. This surfaced two
  real, independent bugs, both fixed in PR #35: `Document.source_channel` only ever allowed
  `"upload"` in both the FastAPI schema and the Angular model, so `GET /quotations/{id}` 500ed for
  this (and any email-captured) quotation — every test fixture had used `source_channel='upload'`,
  so this was never caught; and `_review_reason()` had no check for "extracted literally nothing",
  so a zero-data `succeeded` job silently reached `status='extracted'` — now flagged
  `read_failure`. Second attempt, a properly table-structured PDF built with reportlab's
  `platypus.Table` (real gridlines, standard invoice vocabulary — Vendor/Invoice #/Bill To, an
  Items table with Description/Quantity/Unit Price/Amount columns, a Subtotal/VAT/Total Due
  block): **extracted with complete accuracy**. All three line items matched the source document
  exactly (description, quantity, unit price); header `currency` correctly inferred as `GBP`;
  `stated_total_amount` correctly extracted as `533.00`; `arithmetic_status` correctly
  `reconciled` (250.00 + 160.00 + 123.00 = 533.00). The quotation landed in `in_review`
  (`reason: low_confidence`) because Azure's confidence on the `stated_total` field specifically
  was `0.683`, below the `0.85` threshold — plausibly because the totals block had three rows
  (Subtotal/VAT/Total Due) for Azure to disambiguate — while every line-item field scored above
  `0.95`. This is the confidence-threshold review-routing system working exactly as designed on
  genuinely real extracted data, not a defect. **Proven**: a real, well-formatted document is
  extracted accurately end to end against real hosted Azure DI.

### A second real guardrail bug found while setting up the live-fire test

Preparing to prove guardrail-triggered auto-prepare for real (a fresh RFQ + guardrail, configured
*before* capture, per FR-014's non-retroactivity) surfaced a second genuine, previously-undetected
bug — this one in `_evaluate_guardrails_for_rfq()`'s own price-variance check
(`apps/api/src/procurepilot_api/modules/ingestion/orchestrator.py`), independent of anything found
earlier tonight.

The guardrail compared a candidate line's raw `quotation_line.unit_price_amount` (priced per
quoted pack, e.g. per ream) directly against the price-history baseline (priced per normalised
base unit, e.g. per sheet — `landed_cost.total_amount / landed_cost.normalised_base_quantity`, the
same convention Smart Compare/Savings Ledger/Supplier IQ use everywhere else in this codebase).
For any product whose pack doesn't normalise 1:1 — including `A4 Copy Paper 80gsm`, tonight's own
real test product, packed 2500:1 — this scale mismatch made `price_variance_exceeded` fire on
essentially every real quote, silently blocking guardrail auto-prepare regardless of how
reasonable the actual price was. The existing `test_rfq_guardrails_e2e.py` never caught this
because its seeded product has no `pack_definition` row at all, an implicit 1:1 case.

Fixed in two passes, both independently verified against real Postgres before and after:

- First pass: normalise the candidate line's price using the *matched product's* catalogue
  `pack_definition.base_quantity`. New regression test (seeding a real 1-pack-of-25 product)
  confirmed this fails without the fix and passes with it.
- A GitHub Codex review on the resulting PR correctly flagged a real gap in that first pass: a
  supplier can quote a *different* pack than the catalogue default (`quotation_line` has its own
  `pack_count`/`unit_size`, and `different_pack` is a supported match outcome) — dividing by the
  catalogue's default in that case still normalises onto the wrong scale. Dispatched Codex to fix
  it (prefer the quoted line's own pack when present, falling back to the catalogue default
  otherwise); Codex's sandbox couldn't run tests or commit (read-only filesystem, no network), so
  its staged diff was reviewed and verified independently here — full suite re-run (18 passed),
  one lint issue its sandbox couldn't check for (a fixture-name shadow in the new test) found and
  fixed directly — before committing and pushing.

### A third, more significant finding: guardrail auto-prepare cannot fire in the deployed system

With PR #37 merged and deployed, a fresh RFQ (`5e33cfeb-...`, `A4 Copy Paper 80gsm`, quantity 30)
was sent, a real guardrail (`b2f96bae-...`, 20% price variance, £1000 max, supplier-allowlisted)
configured and enabled *before* any response, and a real reply with the same genuine PDF
attachment sent via Gmail. Traced autonomously as every prior test tonight: real capture, real
extraction (accurate again — `A4 Copy Paper 80gsm`, qty 30, £12.10, reconciled), RFQ status
`responded`. The guardrail did **not** fire (`auto_preparation_event`: none; RFQ stayed
`responded`, never reached `converted`).

Root cause, confirmed by reading `process_inbound_email()` in full, not by inspection of the
guardrail logic alone: `_evaluate_guardrails_for_rfq()` is called **immediately after**
`_insert_extraction_job()` queues the async extraction job — before `_enqueue_extraction()` even
dispatches it to the worker, let alone before the worker completes it. At that point in real
production timing, `quotation_line` has zero rows for the just-captured quotation (extraction
hasn't run yet), so the guardrail's own query always finds no matched lines, `all_lines_matched`
is always `false`, and `_evaluate_candidate()` always returns `partial_line_response` — for every
response, unconditionally, regardless of price, supplier, or any other guardrail condition.
**Guardrail-triggered auto-prepare cannot fire on any genuinely captured RFQ response in the
system as currently wired**, independent of the price-normalisation bugs already found and fixed
above.

`test_rfq_guardrails_e2e.py` (and this session's own `test_rfq_guardrail_pack_normalisation.py`,
modelled on it) never caught this because both monkeypatch `_insert_quotation` to synchronously
insert a pre-matched `quotation_line`/`match_decision` in the same call, simulating "extraction
and matching already completed" — which is never true at the point guardrail evaluation actually
runs against a real captured email, where extraction is asynchronous and takes real seconds.

**Not fixed tonight.** This needs a real design decision — where and when to re-trigger guardrail
evaluation once extraction and matching have actually completed (candidates include: the
extraction-worker re-evaluating guardrails for any RFQ its completed job is tied to, or Match
Resolution's `resolve_match` endpoint re-triggering evaluation after a human confirms a match) —
not a same-night patch, especially on Constitution Principle III territory. Flagged for the
product owner's decision rather than patched unprompted.
