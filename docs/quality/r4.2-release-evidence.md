# R4.2 Release Evidence

Date: 2026-09-24
Release: Grounded Procurement Analyst
Gate posture: G3 remains unmet

## Release Decision

R4.2 is implemented as an advisory release under the existing product-owner exception, the same
posture as R4.0 and R4.1. It answers questions from the tenant's own data only, never places,
drafts, or sends a purchase, and never contacts a supplier. Every turn returns
`release_posture = "g3_unmet"`.

## Delivered Contract

`POST /api/v1/analyst/conversations` starts a new conversation or continues an existing one
(optional `conversation_id`); `GET /api/v1/analyst/conversations` lists conversations
cursor-paginated; `GET /api/v1/analyst/conversations/{conversation_id}` reopens one. Full field
detail is in `docs/architecture/api-specification.md` and `docs/architecture/data-dictionary.md`
(R4.2 sections), architecture rationale in ADR-017.

- Any active tenant member may ask a question (FR-009 restricts *read/continue* access, not who
  may ask a first question).
- Reads (list, get) are scoped to creator, or owner/buyer for tenant-wide oversight — enforced by
  RLS on `analyst_conversation`/`analyst_turn`, not application-layer filtering.
- Continuing a conversation is gated more strictly than the read scope: only the original creator
  may append a follow-up turn, even an owner or buyer gets `404 not_found` on someone else's
  conversation — verified against real Postgres (Phase 5 commit `3dabf20`).
- `POST /analyst/conversations` requires a UUID `Idempotency-Key`; a replayed key returns the
  identical turn rather than creating a second one.
- `analyst_turn` is append-only: authenticated members get `INSERT`/`SELECT` only, no
  `UPDATE`/`DELETE`/`TRUNCATE` grant.
- A cross-tenant or unknown identifier resolves to `NoGroundingData`/`404 not_found`, never leaks
  existence (Non-negotiable #3).

## Business Validation

Four supported question categories (FR-002), one pure retrieval function each in `retrieval.py`
(`retrieve_spend_savings`, `retrieve_supplier_performance_risk`, `retrieve_orders_quotations`,
`retrieve_reorder_forecasts`), architecturally mirroring `supplier_iq_v2.py`: each takes only
typed, pre-scoped input records — no database connection, no tenant lookup — so a cross-tenant or
unknown identifier can only ever resolve to empty input and therefore `NoGroundingData` (FR-007).

Question understanding (`intent.py`) reuses the existing Bedrock/Claude provider pattern
(ADR-004/ADR-014, recorded for R4.2 specifically as ADR-017) to classify a question into a
category and entities only — it never originates the answer's facts, numbers, or citations
(FR-005); those come exclusively from the deterministic retrieval functions. Every numeric answer
shows its calculation (FR-004): the exact input records, the formula, and the result, in the same
`Decimal` arithmetic and explicit-currency discipline as R4.0/R4.1. No cross-currency aggregation
— a mix of currencies is surfaced as a conflict, never silently summed.

A follow-up question that omits its subject ("and last quarter?") resolves using only the
immediately preceding turn's category and entities (FR-008) — never the full conversation
history, and never inherited from an unsupported-refusal prior turn. A follow-up naming its own
subject is always treated as a fresh question regardless of prior context.

FR-003A: an answer concerning an entity with an existing actionable surface carries a deep link to
it — a risky supplier links to its existing negotiation brief (only when one has actually been
generated; never fabricated), a reorder-forecast answer links to the reorder queue, a
spend/savings answer links to the reports center. `orders_quotations` names no such surface in the
spec and carries no link. This is how R4.2 satisfies Constitution Principle IV (every insight
surface carries an executable next step) without violating Principle III (no autonomous
purchasing) — every link points at an existing screen a human already acts on through its own
established authorization flow; R4.2 never creates a new action capability.

## Data and Isolation

Migrations `20260924000001_analyst_conversations.sql`, `20260924000002_analyst_turn_idempotency_and_calculation.sql`,
and `20260924000003_analyst_turn_entities.sql` add `analyst_conversation`, `analyst_turn`, and
`analyst_turn_citation`. All three have forced RLS, tenant-pinned foreign keys, and no
update/delete/truncate grant for any role. `analyst_turn_citation` uses one typed nullable FK
column per source kind (7 columns) with a `num_nonnulls = 1` constraint, mirroring the established
`supplier_scorecard_evidence` pattern, rather than a generic `(source_kind, source_id)` pair.

Dedicated isolation suite (`test_analyst_isolation.py`): cross-tenant invisibility for all three
tables, append-only enforcement (UPDATE/DELETE both raise `InsufficientPrivilege`), cross-tenant
INSERT rejection, and non-owner/non-buyer member read scoping — 8/8 passing against real Postgres.
