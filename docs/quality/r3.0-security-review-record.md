## 1. Webhook signature verification

Two provider modes, `modules/ingestion/webhook_security.py`:

- **Mailgun** (`verify_mailgun_signature`): real HMAC-SHA256 over `timestamp+token`, keyed by
  `MAILGUN_SIGNING_KEY`, compared with `hmac.compare_digest` (constant-time — no timing side
  channel on the comparison itself). No SDK, no network call, matching Mailgun's own documented
  scheme exactly (verified by replaying the real algorithm in `tests/unit/
  test_webhook_security.py` and confirming it validates a signature computed independently).
- **stub / SES** (`verify_shared_secret`): opaque shared secret (`INGESTION_WEBHOOK_SHARED_SECRET`),
  also `hmac.compare_digest`. The module's own docstring is explicit that this is interim, not a
  substitute for Mailgun's real HMAC or a real SNS certificate-chain check — correctly flagged as
  such rather than presented as equivalent.

**Real gap found and fixed**: the HMAC proves Mailgun signed this exact `timestamp+token` pair at
some point — it says nothing about *when*. Nothing checked timestamp freshness, so a single
captured valid webhook call was replayable indefinitely. Message-ID deduplication downstream
(`ingestion_email_log_tenant_message_id_key`, tested in `test_ingestion_orchestrator.py`) stops a
replay from creating a *second quotation*, but does **not** stop it from draining the tenant's
`daily_limit` quota again on every replay, or from creating another raw-email object in the
`ingestion-raw` storage bucket each time. Fixed: `verify_mailgun_signature` now rejects a
timestamp more than `MAILGUN_MAX_TIMESTAMP_SKEW_SECONDS` (default 900s, matching Mailgun's own
documented delivery/retry window) away from real time, checked only *after* the signature itself
verifies — so an attacker without the signing key learns nothing by probing timestamps. 11 new
unit tests (`tests/unit/test_webhook_security.py`) cover both providers: valid/invalid/
missing-config for each, plus stale-past, stale-future, just-inside-the-window, and
non-numeric-timestamp cases for Mailgun specifically. This file had **zero prior test coverage of
any kind** — the existing integration suite (`test_ingestion_webhook.py`) only exercises the
`stub` shared-secret path, never the real Mailgun HMAC function at all.

**Verdict**: **fixed this review** (replay gap), otherwise pass.

## 2. File upload validation

**Type sniffing**: both `capture_service.py` (`_ACCEPTED_MIME_TYPES`) and `catalogue_parser.py`
sniff real bytes (`python-magic` for capture; the CSV/XLSX parser itself for catalogue files) —
neither trusts the client-declared `Content-Type` header or filename extension. Confirmed by
reading both files directly, not by re-deriving from the tests (which already exercise this: a
disguised script uploaded as `.pdf` is caught by `magic.from_buffer`, per `test_email_parser.py`'s
`content_type_mismatch` test for the email-attachment path, and `test_capture_rejects_unsupported_
mime_type` for capture).

**Application-level size limits**: `CAPTURE_MAX_BYTES` (10 MB) and `CATALOGUE_IMPORT_MAX_BYTES`
(25 MB) are both checked in the service layer before the file is processed further, both tested.

**Real gap found and fixed**: nginx (`infra/nginx/nginx.conf`'s `/api/` location) had no
`client_max_body_size` directive, so nginx's own compiled-in default (1 MB) applied — **smaller
than both application-level limits**. Confirmed empirically against the live stack: a 3 MB
multipart POST to `/api/v1/capture` (well under the app's own 10 MB limit) returned nginx's raw
`413` before the request ever reached the FastAPI app at all — no bearer-token check, no app-level
size check, none of the app's own structured `{code, message, details, trace_id}` error envelope,
just nginx's default error page. This means the feature's own advertised and tested upload limits
were **not actually deliverable through the real deployed stack** — every upload between 1 MB and
the app's real limit would silently fail at the proxy layer. Fixed: added
`client_max_body_size 30m;` to the `/api/` location (25 MB largest real limit, plus headroom for
multipart encoding overhead). Re-verified empirically after rebuilding the live web container: the
same 3 MB request now reaches the app (`401`, correctly rejected for the fake bearer token used in
the probe — proving it got *past* nginx and *into* the app's own auth check this time), while a
35 MB request (above the new 30 MB cap) still gets nginx's `413` as intended.

**Verdict**: **fixed this review** (proxy body-size gap), otherwise pass.

## 3. Rate limiting on all ingestion endpoints

Every mutation endpoint carries a dedicated limiter, confirmed by direct grep of
`modules/ingestion/router.py`'s decorators against `config.py`'s real settings:

| Endpoint | Limiter | Default |
|---|---|---|
| `PUT /tenants/email-config`, `POST .../enable`, `POST .../disable` | `rate_limit_ingestion_config_mutation` | 30/minute |
| `POST /webhooks/inbound-email` | `rate_limit_inbound_email_webhook` | 60/minute |
| `POST /capture` | `rate_limit_capture_upload` | 30/minute |
| `POST /suppliers/{id}/catalogue-import` | `rate_limit_catalogue_import` | 10/minute |

The three `GET` endpoints (`/ingestion/emails`, `/suppliers/{id}/catalogue-imports`,
`/ingestion/stats`) carry no rate limiter — confirmed this matches the codebase-wide convention
(no `GET` list/read endpoint anywhere in this codebase is rate-limited, only mutations; already
established as intentional in Wave 4's own review, re-confirmed here rather than assumed).

**Verdict**: pass.

## 4. Tenant isolation in worker jobs

`email_ingestion_worker.py`'s claim/process loop re-derives `tenant_id` strictly from the claimed
`ingestion_jobs` row, never from the job's own `payload` — the same untrusted-payload discipline
`export_worker`/`digest_worker` already established for R2.5. This is proven, not just read: T031's
`test_email_ingestion_worker.py::test_tenant_id_discipline_read_from_job_row_not_untrusted_payload`
inserts jobs whose payload carries a wrong or absent tenant id and confirms processing still uses
the row's real value, with zero rows created under the untrusted payload tenant. The concurrent
claim path (`FOR UPDATE SKIP LOCKED`) is proven exclusive under two genuine overlapping
transactions, not a sleep-based race — re-read directly this review, not taken on faith.

The shared `extraction.py::enqueue_extraction` helper (used by both the email path and capture)
receives `tenant_id` from its caller, which in both cases derives it from a trusted source
(`member.tenant_id` from the verified JWT for capture; the claimed job row for email) — never from
a payload the enqueuing code itself received from outside. What the downstream
`extraction-worker` service does with that payload is out of this review's scope (it is a
separate, pre-existing service this feature does not modify).

**Verdict**: pass.

## 5. Anti-abuse measures

- **Daily email quota**: `_check_and_increment_daily_count` (router.py) is a single atomic
  `UPDATE ... WHERE (daily_count_date <> current_date OR daily_count < daily_limit) RETURNING
  daily_count` — under Postgres's row-level locking, concurrent webhook calls for the same tenant
  serialize against this one statement, so the limit cannot be exceeded by a concurrency race
  (no read-then-write gap; checked and incremented in one round trip). Re-derived directly from
  the SQL, not assumed from the presence of a test.
- **Domain allowlist**: checked *before* the daily-count increment, so a rejected-for-domain email
  does not consume quota — correct ordering, confirmed by reading the router's control flow
  top-to-bottom.
- **No existence/state leak (R10)**: every rejection path in the webhook (unknown recipient,
  disabled tenant, domain not allowlisted, quota exceeded, oversized) returns the identical `202`
  as success — confirmed this is real, not just documented, by reading every `return Response(...)`
  in the handler; all five rejection branches and the success path return the exact same status
  with no distinguishing body.
- **Cross-tenant supplier reference in capture**: `capture_service.py`'s supplier-existence check
  is a bare `select 1 from supplier where id = %s` with no explicit `tenant_id` filter in the SQL
  — but it runs inside `_authenticated_db(settings, member)`, the tenant-claim-carrying connection
  that `supplier`'s own `ENABLE + FORCE` RLS policy applies to. A cross-tenant `supplier_id`
  transparently returns no rows via RLS and correctly 404s — verified this is the same
  rely-on-RLS-not-a-redundant-clause pattern used throughout this codebase (e.g.
  `catalogue_import_service.py`'s identical supplier check), not an oversight.

**Verdict**: pass.

## 6. SQL injection

Every ingestion query reviewed (`router.py`, `capture_service.py`, `catalogue_import_service.py`,
`orchestrator.py`, `email_ingestion_worker.py`) uses parameterized queries (`%s` placeholders,
psycopg's own parameter binding) — no f-string or `.format()`-built SQL anywhere in this module.
`_lookup_tenant_by_address`'s `lower(forwarding_address) = lower(%s)` is parameterized correctly
despite the `lower()` wrapping.

**Verdict**: pass.

## 7. Secret handling

`mailgun_signing_key`, `ingestion_webhook_shared_secret`, and `supabase_service_role_key` are all
`SecretStr` in `config.py`, `.get_secret_value()` called only at the point of use, never logged or
included in any response or audit `target`/`details` payload — confirmed by grep across the whole
`modules/ingestion/` tree for `.get_secret_value()` call sites and checking each one's surrounding
code doesn't leak the resolved value onward.

**Verdict**: pass.

## 8. Audit payload completeness

Every real `_record_audit(...)` call site in `modules/ingestion/` was enumerated directly from
source in T038 (data dictionary), not from a task list — reproduced here for the security review's
own record: `capture_rejected`, `capture_uploaded`, `email_duplicate`, `email_rejected`,
`email_received`, `email_supplier_matched`/`email_supplier_unmatched`, `catalogue_import_started`,
`catalogue_import_completed`/`catalogue_import_failed`, `ingestion.email_config_updated`,
`ingestion.email_config_enabled`/`ingestion.email_config_disabled`. Every mutation and every
worker rejection/success path has a corresponding audit event; the inconsistent naming (most
events unprefixed, the three email-config ones prefixed `ingestion.`) is real but cosmetic, not a
security or completeness gap.

**Verdict**: pass.
