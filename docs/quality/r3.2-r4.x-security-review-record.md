### 1. Reporting readers and audit writer callable across tenants (Critical)

The R2.5 readers are `SECURITY DEFINER`:

- `reporting_savings_for_period`
- `reporting_purchases_for_period`
- `reporting_alert_snapshot`
- `reporting_validity_expiring`
- `reporting_assert_branch_visible`

Each is pinned to `p_tenant_id` on every table reference, but nothing checked that `p_tenant_id` was the
caller's tenant. Migration `20260915000005` revoked EXECUTE from `PUBLIC` only. Supabase grants EXECUTE
on public-schema functions to `anon` and `authenticated` directly, and those grants survived; the hosted
catalog showed `has_function_privilege('anon', …) = true`.

**Reproduction (2026-10-18):** `POST /rest/v1/rpc/reporting_purchases_for_period` with only the anon key
and a test tenant's id returned HTTP 200 and all 11 of that tenant's purchase records. Any signed-in
member could do the same for another tenant's id.

`record_audit_event` had the matching write gap: a caller with no tenant claim could name any tenant.

**Fix (#137):**

- The readers are now guarded wrappers (`assert_caller_tenant`) over the unchanged bodies.
- `record_audit_event` refuses to name a workspace for an `anon` or `authenticated` caller without that
  workspace's claim.
- `AuditWriter` sends workers' events over `DATABASE_URL`.

Tests prove each case and fail without the fix.

### 2. Invitation acceptance via the anon key (High)

`accept_member_invitation(p_token_hash, p_user_id, p_email)` took the user id and the address from its
arguments, and the address is shown on the accept page. Called directly through `/rest/v1/rpc`, it let
anyone holding an invitation link attach the membership to their own account. That defeats the API's
"only the addressee can redeem" check. Invitation links are emailed since #133, but they are still
forwarded and shown on screen.

**Fix (#137):** the API calls the RPC over `DATABASE_URL` after its own sign-up or password check, and
`anon` and `authenticated` lose EXECUTE on it and on the unused `member_invitation_for_token`.

### 3. RFQ authoring and sending not role-restricted (High)

The `POST /rfq`, `PUT /rfq/{id}`, `POST /rfq/{id}/send` and `POST /rfq/{id}/prepare-request` routes
resolved only `current_member`. The `rfq_insert` and `rfq_update` policies checked only the creator. So a
viewer could email suppliers from the business's address, against spec 021 FR-001/FR-003.

**Fix (#138):** `require_role(owner, buyer)` on the four routes, plus the same role check in both
policies.

### 4–5. Outbound webhooks (Medium)

`WebhookSubscriptionCreate.endpoint_url` is a plain `AnyHttpUrl`, and the worker POSTs to it. The
following were therefore all reachable from the worker:

- `http://127.0.0.1`
- `169.254.169.254`
- private ranges
- internal hostnames

`last_error = str(exc)` is listed back to the tenant, which turns a failed delivery into a port probe.

Separately, the worker reads `delivery["event_id"]` from a `d.*` row whose column is `audit_event_id`. So
every delivery fails, and `GET /webhooks/deliveries` fails validation for the same reason. The unit test
hand-built the row with an `event_id` key, which is why it never caught this. Hosted has no webhook
subscriptions, so nothing has been affected yet.

**Fix (#142):**

- https only, with private, loopback and link-local addresses refused at creation and again after DNS
  resolution at delivery.
- Redirects off.
- Generic error categories in place of raw exception text.
- The column fixed.

### 6. OAuth callback not bound to the initiating browser (Medium)

`/pos/connect/callback` (and the accounting equivalent) is unauthenticated and trusts the HMAC-signed
`state`, which carries the tenant. An owner of tenant B could send tenant A's owner B's authorization URL.
If A completes Square consent, A's tokens are stored in B's connection. `_verify_state` also checks only
the age of the state (one hour), not single use.

**Suggested fix:**

- Bind `state` to the browser with an HttpOnly, SameSite cookie, or finish the exchange through an
  authenticated POST from the SPA.
- Consume the nonce once.

### 7. Plaintext fallback for stored provider tokens (Medium)

When `POS_TOKEN_ENCRYPTION_KEY` (or the accounting or webhook key) is empty, `encrypt_token` returns the
plaintext unchanged.

**Suggested fix:** refuse to start when a provider mode other than `stub` is configured without its key,
rather than silently storing tokens in plaintext.

All are described in the table above. The R3.0 record already fixed the unbounded Mailgun replay with a
timestamp window; finding 8 is the remaining in-window case.
