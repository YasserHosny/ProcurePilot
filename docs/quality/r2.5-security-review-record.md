## 1. RLS policy review — `report_schedule` and `digest_subscription`

Both new tables (`supabase/migrations/20260915000002_report_schedule.sql`,
`20260915000003_digest_subscription.sql`) carry:

```sql
alter table <table> enable row level security;
alter table <table> force  row level security;
```

Confirmed by direct grep — both ENABLE and FORCE are present (the migrations format this with a
double space, `force  row level security`, which does not change its effect but is worth noting
for anyone else grepping the same way this review first did and getting a false negative).

**`report_schedule`**: `report_schedule_tenant_select` allows any tenant member to `SELECT` any
schedule in the tenant, not just their own. `report_schedule_owner_buyer_update`/`_delete` allow
any `owner`/`buyer` to mutate any schedule in the tenant, not just their own creation. This is
**verified as intentional, documented design**, not a gap: `specs/012-reporting-hardening/
data-model.md` line 39 states plainly — "RLS: tenant members may select; owner/buyer may
insert/update/delete" — with no per-creator restriction specified. `ReportsService.list_schedules`
(schedules.py) matches this exactly: it runs `select * from report_schedule` with no membership
filter at all, relying entirely on RLS, consistent with the documented team-visibility model
(schedules are configuration, not personal state — see the table's own `comment on table`).

**`digest_subscription`**: `digest_subscription_member_select` restricts non-owners to their own
`membership_id`, with owners seeing every row — matching the table's own comment ("Members see
only their own rows; owners see every row in the tenant") and `DigestsService.list_subscriptions`
(service.py lines 43-91), which branches identically in the application layer. Insert/update/delete
policies all pin `membership_id = current_membership_id()`, so one member cannot mutate another
member's subscription even within the same tenant. INSERT has `WITH CHECK`; UPDATE has both
`USING` and `WITH CHECK`; DELETE has `USING`. Every policy on both tables is tenant-pinned via
`tenant_id = current_tenant_id()`.

**Verdict**: both tables pass. The application-layer query shape and the RLS policy shape agree
with each other and with the documented data model in every case checked.

## 2. Worker tenant re-derivation

Both R2.5 background workers treat their queue payload as an untrusted hint, per FR-007, and were
checked line-by-line:

- `export_worker.process_export_job` (`workers/export_worker.py` lines 22-45): re-reads
  `export_job` by `job_id`, takes `real_tenant_id` from the DB row, and — only if the queue
  payload also carried a `tenant_id` — compares it to the real value, raising
  `RuntimeError("tenant_payload_mismatch")` on a mismatch rather than trusting the payload.
- `digest_worker.process_digest_subscription` (`workers/digest_worker.py` lines 49-85): same
  pattern, explicit `if UUID(str(sub["tenant_id"])) != tenant_id: ... return "tenant_mismatch"`,
  with the mismatch logged before rejection.
- The tick-based claim paths (`_claim_due_schedules`, `_claim_due_subscriptions`) never consume
  external payloads at all — they claim rows directly off the DB via `FOR UPDATE SKIP LOCKED`, so
  there is no untrusted input to re-derive against in the first place.
- The producer side agrees with the consumer side: `report_scheduler._enqueue_job` (line 158)
  passes `job_id` and `UUID(str(schedule["tenant_id"]))` — both read from the just-claimed real
  `schedule` row, never from anything caller-supplied.
- Actor identity for audit events is likewise DB-derived: `export_worker._record_worker_audit`
  calls use `UUID(str(row["requested_by"]))`, read from the export_job row, not a payload field.

**Verdict**: pass. Both workers correctly treat the queue as a hint, not an authority, end to end.

## 3. Authorization-pinned reader review

The three R2.5 reader functions in `supabase/migrations/20260915000005_reporting_reader_
functions.sql` were read in full:

- `reporting_savings_for_period`: every join (`purchase_record`, `workspace_product`, `supplier`,
  the `purchase_request`/`branch` lateral join) is pinned with `and <table>.tenant_id =
  p_tenant_id`. `canonical_product` is the one unpinned join, correctly so — it is a
  tenant-independent shared reference table (workspace_product already pins the tenant boundary
  one join earlier).
- `reporting_purchases_for_period`: same shape, checked directly — every tenant-scoped table in
  the join tree carries the `p_tenant_id` pin.
- `reporting_alert_snapshot`: every join in both the `lineage` CTE and the final select
  (`workspace_product`, `match_decision`, `landed_cost`, `quotation_line`, `quotation`,
  `supplier`, `pack_definition`) is tenant-pinned. One real finding here, investigated and
  resolved as **not a bug**: `p_period_start`, `p_period_end`, and `p_branch_id` are declared
  parameters that the function body never references. Initially flagged as a filter-bypass risk
  during this review; checking `specs/012-reporting-hardening/spec.md`'s own "Assumptions"
  section (line 348) resolved it — "`alerts_summary` ... [is] computed from live alert conditions
  at generation time, consistent with R2.4's dismissal-only alert model; no alert rows are
  persisted by reporting" is an explicit, documented design choice, not an oversight. Alerts have
  no branch attribution in this data model either (the Python-side row mapping in
  `export_worker._fetch_report_rows`'s `alerts_summary` branch hardcodes `"branch_name": "—"` for
  the same reason), so `p_branch_id` being unused is consistent with that same documented
  boundary. No fix applied — the function is correct against its own spec.

All three functions are `security definer` with `set search_path = pg_catalog, public` (blocking a
search-path hijack) and `stable` (no writes possible from a reporting path).

**Verdict**: pass, with one initially-suspected finding downgraded to "verified by design" after
checking the spec rather than assuming the code was wrong.

## 4. Signed-URL TTL and storage bucket policy

`export_download_url_ttl_seconds` (`config.py`) is a required, bounded setting: `Field(default=300,
ge=60, le=3600)` — a caller cannot configure a TTL outside 60s–3600s, and `ExportStorage.
create_signed_url` passes it straight through with no override path.

**Real finding, fixed in this review**: no migration created the `exports` storage bucket at all.
`ExportService`/`ExportStorage` have referenced `settings.supabase_exports_bucket` (default
`'exports'`) since Wave 16, and every other tenant-scoped bucket in this codebase has a creation
migration plus a `storage.objects` tenant-isolation policy (`quotation-documents`:
`20260819000020_quotation_storage.sql`; `quality-issue-photos`:
`20260913000005_quality_issue_photo_storage.sql`) — `exports` had neither. A fresh environment
applying every migration in order would have no bucket for exports to land in, and even a
manually-created bucket would have had no second isolation boundary beyond the signed-URL check
in `ExportService.create_download_url`, which is exactly the gap
`20260819000020`'s own comment warns against: "a leaked or guessed object path would bypass table
RLS entirely if the bucket itself had no policy." Fixed via
`supabase/migrations/20260916000001_exports_storage.sql`: creates the bucket with `public =
false`, and adds `exports_tenant_isolation` on `storage.objects` — the path shape here is
`{tenant_id}/savings/{job_id}.{format}` (no `tenants/` prefix, unlike the other two buckets), so
the policy pins `(storage.foldername(name))[1]` rather than `[2]`; copying the other buckets'
policy verbatim without adjusting the index would have written a policy that silently checked the
wrong path segment. Applied and verified against a disposable Postgres instance (clean re-apply,
no errors) and confirmed the full backend suite still passes (1005 passed, 2 known pre-existing
failures unrelated to this change).

**Verdict**: TTL bound passes. Bucket/policy gap found and fixed, not merely documented.

## 5. Purge and download-link invalidation

`report_scheduler._purge_expired_artifacts` (lines 196-254): selects `export_job` rows past
`expires_at`, calls `ExportStorage.delete_object` on the real storage object first, then updates
the row to `status = 'expired'` **and nulls `storage_bucket`, `storage_path`, `download_url`**,
and records a `reports.artifact_purged` audit event. `ExportService._enforce_download_visibility`
(service.py lines 129-141) refuses any download whose `status != 'completed'` or whose
`storage_bucket`/`storage_path` is `None` — so a purged artifact's ID resolves to `NotFoundError`
on every subsequent download attempt, not a stale or broken link. Verified the delete-then-null
ordering is right: the object is removed from Storage before the row stops pointing at it, so
there is no window where the row claims a live object that Storage no longer has.

**Verdict**: pass.

## 6. Rate-limit review (T035)

Export creation, schedule mutations (create/update/delete), and digest-subscription mutations
(create/update/delete) are all rate-limited via `shared/rate_limit.mutation_limiter`, keyed by
`tenant_member_rate_limit_key` — verified tenant + member claims from the real bearer token when
present, IP fallback only when it is not. Independently, active-row caps
(`active_schedule_cap_per_member`, `active_digest_subscription_cap_per_member`) block unbounded
accumulation of *standing* recurring jobs regardless of creation rate. Both mechanisms have
integration tests proving the structured 429/422 response and that no row/queued-work survives a
refused request (`apps/api/tests/integration/test_mutation_rate_limits.py`,
`test_active_resource_caps.py`) — see T035 in `specs/012-reporting-hardening/tasks.md`.

**Verdict**: pass (implemented and verified in this same wave, not carried over from an earlier
one).

## 7. SMTP secret handling and log redaction

`smtp_password` (`config.py`) is `SecretStr | None`; `digest_worker._deliver_via_smtp` calls
`.get_secret_value()` only at the point of SMTP login (line 265), never logs it, and never
includes it in any return value. The failure path (lines 218-228) deliberately discards the real
exception text — `safe_err = f"{type(exc).__name__}: delivery_failed"` — before it reaches either
the log or the audit `detail` field, so no SMTP library error message (which could in principle
echo back connection or auth details) ever reaches a log line or a stored audit row.

**Verdict**: pass.

Every R2.5 lifecycle action was enumerated directly from source (not from the spec's own list, to

`reports.export_requested`, `reports.artifact_downloaded`, `reports.artifact_purged`,

`digests.subscription_provisioned`.

Every mutation, every worker state transition, and every download/purge event has a corresponding
entry — create/read(download)/update/delete are all covered for both schedules and subscriptions,
and the export-job lifecycle (enqueue → run start → run complete or fail → purge) is fully audited
end to end.

**Verdict**: pass.

## 9. `audit_event` append-only re-check

`revoke update, delete on audit_event from authenticated, anon;` and `... from public;`

**Verdict**: pass, unchanged from the original P1 guarantee.
