# R2.5 Security and Hardening Critique

Date: 2026-09-14

Author: Codex security critique (delegated), reviewed by the orchestrator

## Summary Verdict

R2.5 is directionally sound, but implementation should not start until the plan tightens the
service-role worker boundary, scoped visibility rules, and audit payload requirements.
The largest risk is that claimless workers plus tenant-pinned SECURITY DEFINER readers become
an alternate query layer whose authorization semantics drift from member-visible APIs.
The current tasks include isolation tests, but they need branch/member visibility, stale artifacts,
queue replay, and storage policy cases to prove the non-leakage claims.
Secret handling and rate limits are present as requirements, but several settings and bucket
controls need explicit task-level acceptance criteria.

## Numbered Findings

1. **Severity: blocker | Area: report/export tenant-isolation risks**

   **Evidence:** Constitution Principle V requires tenant isolation by database construction and
   automated cross-tenant integration tests. `specs/012-reporting-hardening/spec.md` FR-004,
   FR-005, FR-018, and FR-019 require Reports listing, signed downloads, RLS, and not-found
   semantics. `specs/012-reporting-hardening/data-model.md` gives `report_schedule` member-wide
   select, `digest_subscription` self-select plus owner visibility, and a Reports cursor over
   `export_job`. Existing `supabase/migrations/20260821000034_value_proof_rls.sql` gives
   `export_job` one permissive `for all` tenant policy, not branch/member-scoped visibility.

   **Critique:** The plan asserts cross-tenant isolation, but does not yet specify branch-scoped
   visibility for artifacts, schedule filters, export rows, or digest content. A branch buyer could
   potentially list another branch's artifact metadata through `GET /reports/artifacts` if the API
   relies only on tenant RLS. The same risk exists for the artifact cursor and source schedule id:
   metadata such as kind, period, row count, branch filter, schedule ownership, and completion
   cadence can leak commercial activity even when storage downloads are blocked. Existing branch
   migrations show this project has already learned that a permissive tenant policy plus a second
   permissive visibility policy is OR-combined and can bypass narrower scoping.

   **Recommendation:** Before Wave 16 implementation, amend FR-004, FR-018, FR-019, T002, T003,
   T004, T008, T012, and T019 to define scoped visibility explicitly: Reports artifact listing and
   downloads must enforce tenant, branch visibility, and membership ownership where applicable,
   using restrictive RLS policies or a single combined policy shape rather than API-only filters.
   T008 should include tenant A/B, branch A/B, owner/buyer/member, schedule owner, artifact cursor,
   expired artifact, purged artifact, and signed-download cases.

2. **Severity: blocker | Area: scheduled job impersonation and service-role boundaries**

   **Evidence:** `specs/012-reporting-hardening/research.md` R4 uses `FOR UPDATE SKIP LOCKED`,
   deterministic RQ job ids, and a unique export index for idempotency. R5 runs scheduled generation
   and digest delivery without a member JWT using service-role plus tenant-id parameters.
   `apps/api/src/procurepilot_api/workers/export_worker.py` currently receives `job_id` and
   `tenant_id` from Redis, calls `_act_as_tenant`, and updates any runnable job by id.
   `apps/api/src/procurepilot_api/modules/exports/service.py` enqueues deterministic job id
   `str(row["id"])`.

   **Critique:** R5 is the highest-risk design choice and is under-specified for queue poisoning,
   replay, and tenant/job mismatch. If an attacker gains Redis write access, SSRF into Redis, or a
   confused internal enqueue path, a payload can pair tenant A with job B unless the worker
   re-derives tenant ownership from Postgres and refuses mismatches before any read, render, upload,
   or audit. Deterministic job ids reduce duplicate enqueue, but they are also predictable replay
   handles. `FOR UPDATE SKIP LOCKED` handles scheduler races, but not stale claimed rows, replayed
   RQ payloads, or a worker crash after storage upload before DB completion.

   **Recommendation:** Amend FR-007, T016, T017, T023, T024, and T036 to require workers to treat
   queue payloads as untrusted hints: load the schedule/subscription/export row by id, derive
   `tenant_id` from the row inside the transaction, verify status and due period, and pass that
   derived tenant to reader functions. Add tests for tenant/job mismatch payloads, duplicate RQ
   replay, stale due claims, crash-after-upload recovery, and deterministic job-id collision. The
   scheduler claim should record a lease or claimed timestamp if more than one scheduler instance
   may exist in production.

3. **Severity: major | Area: report/export tenant-isolation risks**

   **Evidence:** `specs/012-reporting-hardening/data-model.md` introduces tenant-pinned
   SECURITY DEFINER functions for savings, purchases, alerts, and expiring validity, each taking
   `tenant_id` and filters. The precedents in
   `supabase/migrations/20260819000007_audit_writer.sql` and
   `supabase/migrations/20260819000009_member_invitations.sql` narrowly validate authority inside
   the function and pin `search_path`. `specs/012-reporting-hardening/tasks.md` T005 only names
   tenant-id parameters and `SET search_path`.

   **Critique:** The proposed reader functions are described as tenant-pinned, not
   authorization-pinned. That is weaker than R3's claim that digest content is computed from data
   the member's own role already permits. A claimless worker cannot rely on member RLS unless the
   function also accepts and validates membership/role/branch scope, or joins to branch-role
   tables internally. Otherwise a per-member digest can accidentally become a tenant-wide digest,
   especially for owners selecting all subscriptions or branch filters.

   **Recommendation:** Amend FR-007, FR-008, FR-018, T005, T008, T017, T023, T024, and T036 so
   reader functions take the effective membership id and optional branch id where member-specific
   visibility matters, then validate active membership and branch visibility internally. The
   isolation test must include a branch-scoped buyer whose digest and scheduled report cannot
   include another branch's savings, purchases, alerts, or expiring offers.

4. **Severity: major | Area: audit events**

   **Evidence:** `specs/012-reporting-hardening/data-model.md` lists schedule, run, download,
   purge, subscription, and delivery audit actions. `apps/api/src/procurepilot_api/shared/audit.py`
   records `trace_id`, actor fields, outcome, and redacted target through
   `record_audit_event`. `specs/012-reporting-hardening/spec.md` FR-005, FR-007, FR-011, and
   FR-014 require download, generation, delivery, and purge audit events.

   **Critique:** The event list is close, but the payload contract is not complete enough for a
   security record. It does not require trace ids on worker-triggered events, actor semantics for
   system actions, source schedule/subscription ids, period windows, filters digest, row count,
   storage bucket/path hash, signed-url TTL, SMTP recipient membership, delivery provider response
   class, purge reason, or previous/new schedule state. Without these fields, incident response
   can show that something happened but not prove which tenant-scoped data was generated, sent,
   downloaded, or purged.

   **Recommendation:** Amend FR-005, FR-007, FR-011, FR-014, T012, T013, T016, T017, T024, and
   T036 to define mandatory audit target fields per action. Use `actor_membership_id` for member
   actions and an explicit system actor marker in `target` for scheduler/digest/purge workers.
   Require trace ids or generated correlation ids for all worker paths, and record refused
   download attempts for expired, purged, and cross-scope ids without revealing existence in the
   HTTP response.

5. **Severity: major | Area: secret-handling risks**

   **Evidence:** Constitution quality gates forbid secrets in the repo. `apps/api/src/procurepilot_api/config.py`
   stores current secrets as `SecretStr`, but has no SMTP, signed-url TTL, row-cap, or retention
   settings yet. `specs/012-reporting-hardening/research.md` R6 makes signed URL TTL
   environment-configured; R7 adds SMTP credentials from environment; R8 commits an OFL Arabic
   font; R12 keeps gitleaks and adds dependency audits. `apps/api/src/procurepilot_api/modules/documents/service.py`
   hardcodes document download signed URLs to 300 seconds.

   **Critique:** The plan says environment-configured but does not specify validation bounds,
   secret typing, `.env.example` placeholders, or CI scanning scope for the new variables and font
   asset. A too-long signed URL TTL materially weakens purge/expiry promises. SMTP password,
   username, and DSN-like host strings must be redacted in logs and audit error details. The font
   commitment is acceptable only if license files are committed and gitleaks does not skip binary
   assets or generated renderer outputs where test fixtures might embed secrets.

   **Recommendation:** Amend FR-005, FR-010, FR-014, FR-015, T013, T015, T024, T034, and T036 to
   require `SecretStr` for SMTP password/username where appropriate, bounded integer settings for
   signed-url TTL and retention, no hardcoded production fallback, `.env.example` placeholders only,
   log/audit redaction tests, and committed font license metadata. T036 should verify export bucket
   privacy, signed-url max TTL, and that purge invalidates links even if a previously issued URL
   has not naturally expired.

6. **Severity: major | Area: abuse and rate-limit risks**

   **Evidence:** Roadmap §10.8 requires per-endpoint SlowAPI limits. `apps/api/src/procurepilot_api/shared/rate_limit.py`
   currently keys limits by client IP and only exposes `auth_rate_limit`; `rg` shows current
   decorators are applied only in auth routes. `specs/012-reporting-hardening/spec.md` FR-020
   requires rate limits for export creation, schedule mutations, and digest subscription mutations.
   `specs/012-reporting-hardening/tasks.md` T035 says to extend the shared rate-limit helper.

   **Critique:** IP-based limits are insufficient for authenticated multi-tenant abuse, especially
   behind NAT or a reverse proxy. R2.5 introduces expensive render paths, 10k-row exports, schedule
   churn, digest sending, and mutation endpoints that can flood Redis, SMTP, storage, and audit
   rows. The plan does not yet define per-member, per-tenant, per-recipient, and scheduler-side
   quotas, nor does it cap active schedules/subscriptions per member or tenant.

   **Recommendation:** Amend FR-020 and T035 to define named limits and keys: export creation per
   member and tenant, schedule mutations per member, active schedules per tenant/member, digest
   subscription mutations per member, digest deliveries per recipient per period, and worker enqueue
   caps per tick. Add integration tests proving over-limit structured 429 responses and no queued
   work. Prefer a key function that uses verified tenant and membership claims where available,
   with IP only as a fallback.

7. **Severity: major | Area: append-only and retention requirements**

   **Evidence:** Constitution Principle II prohibits destructive updates to outcome records;
   `audit_event` is append-only per `supabase/migrations/20260819000004_rls.sql`.
   `specs/012-reporting-hardening/research.md` R9 keeps `export_job` rows and marks them
   `expired` while deleting stored bytes. `specs/012-reporting-hardening/data-model.md` keeps
   schedules hard-deletable configuration and mutates `export_job` through queued/running/completed/
   failed/expired statuses.

   **Critique:** Updating `export_job` status is acceptable for a job table only if the immutable
   audit trail captures lifecycle transitions. The plan does not yet distinguish mutable job state
   from append-only evidence, nor does it require preserving storage object identity after purge
   beyond bucket/path columns. Hard-deleting schedules is probably acceptable as configuration, but
   deleting a schedule that generated artifacts can impair replay unless schedule snapshots are
   fully copied into each export job and audit event.

   **Recommendation:** Amend FR-006, FR-014, FR-016, T004, T012, T016, T017, T036, and T038 so
   every generated artifact stores immutable schedule/filter/rule snapshots independent of the
   schedule row, and every status transition writes an audit event. Purge should update only
   `status`, `expires_at`/purge metadata, and storage deletion fields needed for history; it must
   never delete `export_job` rows or audit rows. Add a check that `audit_event` still has no update
   or delete grants after R2.5 migrations.

8. **Severity: minor | Area: secret-handling risks**

   **Evidence:** `apps/api/src/procurepilot_api/modules/exports/storage.py` currently stores export
   objects at `{tenant_id}/savings/{job_id}.{format}`, sets content type for XLSX/PDF only, and
   returns the still-unimplemented `/api/v1/exports/{job_id}/download` path. `specs/012-reporting-hardening/spec.md`
   FR-012 adds CSV and additional kinds. `specs/012-reporting-hardening/research.md` R6 and R12
   call for signed URL and bucket policy review.

   **Critique:** Storage paths and content types are implementation details, but R2.5 is changing
   enough formats and kinds that the plan should require deterministic, non-secret object paths
   that cannot be confused across kinds. CSV needs explicit `text/csv; charset=utf-8` handling,
   and storage metadata should avoid putting supplier names, branch names, emails, or filter values
   in object paths. The exports bucket must remain private with signed URL access only.

   **Recommendation:** Amend T013, T014, T016, T017, and T036 to specify path shape
   `tenants/{tenant_id}/exports/{job_id}.{format}` or equivalent, no user-supplied path segments,
   correct content types for CSV/XLSX/PDF, no PII/commercial labels in paths, private bucket policy,
   and a storage policy regression check.

## Recommendation for Wave 16

**Must change the spec/tasks before implementation:** Findings 1, 2, 3, 4, 5, and 6 should update
FR-004, FR-005, FR-007, FR-008, FR-010, FR-011, FR-014, FR-018, FR-019, FR-020, and the mapped
tasks before coding starts. These are design-boundary issues; reviewing them after code exists
will be more expensive and easier to miss.

**Implementation-review checkpoints:** Findings 7 and 8 can be enforced during implementation
review if their acceptance criteria are added to T004, T013, T014, T016, T017, T036, and T038.
The reviewer should inspect migrations for restrictive/combined policy shape, worker code for
tenant re-derivation, storage code for private signed access, and tests for replay and purge
behavior.

**Wave 18 security-record items:** The dependency audit allowlist, final bucket-policy evidence,
SMTP provider operational runbook, font license record, and penetration-test procurement notes
should be carried into the Wave 18 security record if they are not needed to unblock the Wave 16
implementation branch. The R2.5 security review record should still contain pass/fail evidence
for every FR-022 checklist item before release.
