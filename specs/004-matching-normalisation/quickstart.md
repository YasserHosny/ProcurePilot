# Quickstart: Matching and Normalisation

**Feature**: 004-matching-normalisation | **Date**: 2026-08-21

Assumes chunks 4.1, 4.2 and 4.3 are already working. Start there if auth, tenancy, catalogue,
suppliers, quotation upload or extraction review are not running yet:

- [`../001-platform-foundation/quickstart.md`](../001-platform-foundation/quickstart.md)
- [`../002-catalogue-suppliers/quickstart.md`](../002-catalogue-suppliers/quickstart.md)
- [`../003-quotation-inbox-extraction/quickstart.md`](../003-quotation-inbox-extraction/quickstart.md)

This chunk adds no new docker-compose service. Matching and landed-cost computation live inside
`apps/api` as `matching` and `landed_cost` modules; there is deliberately no
`services/matching-worker`.

---

## 1. Bring the stack up

```bash
docker compose up --build
pnpm db:migrate
pnpm db:seed
```

For this chunk, the existing API, web app and local Supabase services are enough. Redis and
`services/extraction-worker` may still be present from chunk 4.3 for extraction, but matching does
not add another worker.

## 2. Prepare catalogue data

Create or import products in the catalogue first. At least one product should have:

- a workspace product row
- a pack definition with a base unit
- an alias if you want to test the exact-alias auto-accept path

Remember that `pack_definition.base_quantity` is generated by the database. Matching reads it for
normalisation; it does not write it.

## 3. Review a quotation

Upload and extract a quotation as in chunk 4.3. Correct any extraction fields, confirm the supplier,
and then confirm the quotation:

```bash
POST /api/v1/quotations/{quotation_id}/confirm
```

Only `quotation.status = reviewed` lines are matchable. A quotation that is still `extracted` or
`in_review` is not trusted input for matching.

## 4. Inspect automatic matches

Open the quotation match state:

```bash
GET /api/v1/quotations/{quotation_id}/matches
```

Lines with exact GTIN, supplier-code or alias hits should have ranked candidates with confidence
and structured reasons. If the top candidate meets the configured auto-accept threshold and is not
a close call, the response includes a `match_decision` with `is_automatic = true`.

## 5. Work the match queue

Open the standalone queue:

```bash
GET /api/v1/match-tasks?status=open&limit=50
```

Each task shows the source quotation line, ranked candidates, confidence and reason breakdown.
Resolve a line as owner or buyer:

```bash
POST /api/v1/quotation-lines/{line_id}/match
```

You can confirm the same product, choose a different pack, choose a different variant, mark a
compatible alternative, or choose `no_match_new_product`. The no-match path creates a product
inline using the same product-create shape as chunk 4.2.

After a human decision, the exact supplier wording from `quotation_line.original_text` is inserted
or reused as a `product_alias`. If that lowercased wording already points at the same product, it is
reused. If it already points at a different product, this chunk refuses the alias conflict rather
than overwriting it.

## 6. Check landed cost

Once a line has a decision, read its landed cost:

```bash
GET /api/v1/quotation-lines/{line_id}/landed-cost
```

The response shows unit price, derived VAT amount, delivery fee, discount, zero other charges,
normalised quantity, total, raw inputs and the rule version, initially `landed-cost-v1`.

For chunk 4.4:

```text
vat_amount = unit_price_amount * quantity * vat_rate
landed_cost = (unit_price_amount * quantity)
            + vat_amount
            + delivery_fee_amount
            - discount_amount
            + 0 other_charges
```

No currency conversion happens. The landed cost is in the quotation line's own currency.

## 7. Verify the guarantees

```bash
# Cross-workspace isolation, extended to candidates, tasks, decisions and costs
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:54322/postgres pnpm test:isolation

# API contracts, matching pipeline and landed-cost replay
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:54322/postgres pnpm test:api

# Web match-resolution queue, keyboard navigation and accessibility
pnpm test:web
pnpm test:e2e
pnpm test:a11y
```

The matching evaluation harness for this chunk lives under `ml/evals/` at implementation time and
runs against the versioned benchmark under `ml/benchmarks/`. It must report precision at
auto-accept, recall, review-band size, alias hit rate and Expected Calibration Error against 500+
labelled product-match pairs including hard negatives.

## Common problems

**A quotation has no matches.** Check the quotation status first. Matching consumes only reviewed
quotations, not extracted or in-review quotations.

**A line with good candidates still entered the queue.** The top score may be below
`MATCHING_AUTO_ACCEPT_THRESHOLD`, or the top two candidates may be within `MATCHING_REVIEW_MARGIN`.
Close calls go to a human rather than being guessed.

**Landed cost is missing.** The line needs a `match_decision` first. Candidates alone are not a
match.

**VAT looks absent.** `quotation_line` stores `vat_rate`, not `vat_amount`. A missing VAT rate is
treated as zero for `landed-cost-v1`.

**Other charges are zero.** Correct for this chunk. Other charges are not modelled in chunk 4.4 and
can be added under a later rule version.

**An alias conflict blocks resolution.** The exact lowercased wording already belongs to another
product in this workspace. Correcting or retiring a previously confirmed alias is outside this
chunk.

## What is deliberately absent

- A separate matching worker service
- Offer comparison, recommendations, basket building or quantity-threshold recalculation
- Historical price aggregation such as last-paid or average-paid
- Savings verification or savings ledger entries
- Alias correction or retirement
- Currency conversion
